# UI Sweep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring every `app/(app)/` screen (list, detail, form, settings) onto shadcn's `Select`/`Checkbox`/`Card` primitives and a shared `PageHeader`, replacing raw HTML `<select>`/`<input type="checkbox">` and hand-rolled `<div>`/`<section>` layouts.

**Architecture:** No data/permissions/domain logic changes — this is presentation-layer only. A new `PageHeader` component replaces every page's hand-copied `<h1>`. Every raw `<select>` becomes shadcn's `Select` (Base UI under the hood); the one raw checkbox becomes shadcn's `Checkbox`. List pages wrap their filter toolbar + table in one `Card`; detail pages group each display section (Activity, Comments, Attachments, linked-item lists) into its own `Card`, leaving action controls (status/operation controls) un-carded directly under the header; form pages wrap the form in one `Card`.

**Tech Stack:** Next.js 16 (App Router), React 19, `@base-ui/react` v1.7 (via the shadcn `base-nova` style's `components/ui/*` wrappers), `react-hook-form` + `zodResolver`, vitest + `@testing-library/react` + `@testing-library/user-event`.

**Spec:** `docs/superpowers/specs/2026-09-25-ui-sweep-design.md`

## Global Constraints

- No change to any domain function, API route, permission check, or validation schema — every task is presentation-only.
- Every raw `<select>`/`<option>` becomes `Select`/`SelectTrigger`/`SelectValue`/`SelectContent`/`SelectItem` from `@/components/ui/select` (already installed — do not run the shadcn CLI).
- The one raw `<input type="checkbox">` (`employee-form.tsx`) becomes `Checkbox` from `@/components/ui/checkbox` (already installed).
- `react-hook-form` fields driven by a `Select`/`Checkbox` must use `Controller` (`register()` does not work on a non-native input) — every swapped form field needs this.
- Top-level page flow uses `gap-6`; multi-`Card` internal spacing uses `gap-4`, matching the dashboard's existing convention.
- `next build`, `tsc --noEmit`, and `pnpm lint` must stay clean after every task.
- Never commit directly to `main` — this plan executes on branch `worktree-ui-sweep-plan`.

## Review Focus

- **Filter-select "All X" round-trip:** after picking a specific status/priority/category/department and then picking "All X" again, the list must show unfiltered results again — a reasonable person filtering a table expects "All" to actually clear the filter, and a wrong sentinel-to-empty-string mapping would silently leave the last filter stuck. Pinned in Task 2 (`TaskListView`) and reused unchanged in every later list-view task.
- **Optional relation Selects submit `undefined`, not the sentinel string:** creating an employee/operation/asset with department/location/manager left on "No department" must submit no `departmentId` at all (matching today's `setValueAs: (v) => v || undefined` behavior) — a wrong mapping would send the literal string `"none"` to the API and fail Zod validation. Pinned in Task 5 (`EmployeeForm`).
- **Required-enum Selects with a pre-set default still submit that default untouched:** `OperationForm`'s priority (`medium`), `RequestForm`'s category (first `REQUEST_CATEGORIES` entry), and `EmployeeForm`'s role (`employee`) must still be submitted correctly when the user never opens the dropdown — a `Controller` wired to local state instead of `field.value`/`field.onChange` would silently submit `undefined` and trip Zod. Pinned in Task 4 (`OperationForm`) and reused in Tasks 3/5.
- **The checkbox's default-checked value still submits `true` untouched:** `EmployeeForm`'s "Start onboarding workflow" currently relies on `defaultChecked` on a native input; after the `Controller` swap it must come from `useForm`'s `defaultValues: { startOnboarding: true }` instead, or a create-without-touching-it submission silently flips to unchecked. Pinned in Task 5.
- **Rewritten combobox tests still exercise the same assertion, not a weaker one:** each of the 8 tests rewritten off `fireEvent.change`/`selectOptions` must still assert the same submitted request body / disabled-while-loading state it did before — a rewrite that only makes the test pass without exercising the real interaction would hide a regression. Pinned per-file in Tasks 2, 3, 4, 5, 6, and 10.

## Select-swap conventions used throughout this plan

Four patterns cover every raw `<select>` in scope. Each task below states which pattern applies to which field — this section is the canonical code for each, referenced by name (not by page number) so no task needs to guess.

**Pattern A — filter select with an "All X" clear option** (list-view status/priority/category/department filters):

```tsx
<Select
  value={status || "all"}
  onValueChange={(value) => setStatus(value === "all" || value === null ? "" : value)}
>
  <SelectTrigger className="w-40">
    <SelectValue />
  </SelectTrigger>
  <SelectContent>
    <SelectItem value="all">All statuses</SelectItem>
    {STATUS_OPTIONS.map((option) => (
      <SelectItem key={option} value={option}>
        {formatOptionLabel(option)}
      </SelectItem>
    ))}
  </SelectContent>
</Select>
```

The `status` state variable itself is untouched (still a plain string, `""` meaning "all") — only the `Select`'s own `value`/`onValueChange` map `"" ↔ "all"` at the presentation boundary. **Important:** Base UI's `onValueChange` signature is `(value: string | null, eventDetails) => void` — `value` is typed nullable even though no item here ever has `value={null}`. The `value === null` branch is required for `tsc` to accept the assignment to a plain `string`-typed setter (`setStatus`/`setDepartmentId`/etc. all take a plain `string`, not `string | null`) — omitting it produces `Type 'string | null' is not assignable to type 'SetStateAction<string>'`.

**Pattern B — optional relation picker with an explicit "No X" option** (create-form department/location/manager fields), wired through `Controller`:

```tsx
<Controller
  name="departmentId"
  control={control}
  render={({ field }) => (
    <Select
      value={field.value ?? "none"}
      onValueChange={(value) => field.onChange(value === "none" || value === null ? undefined : value)}
    >
      <SelectTrigger id="departmentId" className="w-full">
        <SelectValue />
      </SelectTrigger>
      <SelectContent>
        <SelectItem value="none">No department</SelectItem>
        {departments.map((department) => (
          <SelectItem key={department.id} value={department.id}>
            {department.name}
          </SelectItem>
        ))}
      </SelectContent>
    </Select>
  )}
/>
```

The `value === null` branch is defensive, not required by `tsc` here (react-hook-form's `field.onChange` is loosely typed and accepts `string | null` without complaint) — included anyway so a stray `null` from Base UI can never leak into the form state as a real value where the rest of the codebase (Zod schemas, `setValueAs` mappings elsewhere) expects `undefined` for "no selection."

**Pattern C — required enum select with a pre-set default**, wired through `Controller`:

```tsx
<Controller
  name="priority"
  control={control}
  render={({ field }) => (
    <Select value={field.value} onValueChange={field.onChange}>
      <SelectTrigger id="priority" className="w-full">
        <SelectValue />
      </SelectTrigger>
      <SelectContent>
        {PRIORITY_OPTIONS.map((option) => (
          <SelectItem key={option} value={option}>
            {option}
          </SelectItem>
        ))}
      </SelectContent>
    </Select>
  )}
/>
```

`field.onChange`'s loose typing (it accepts `string | null` without complaint) is also why Pattern C needs no `value === null` handling — verified by `tsc` staying clean on `RequestForm`'s Controller-wrapped category select once implemented.

**Pattern D — plain `useState` picker for a "pick one then click a button" control** (not react-hook-form; operation-link pickers, asset-assign, request-reassign). The existing `useState("")` becomes `useState<string | undefined>(undefined)` so an unmatched empty string is never passed to `Select`:

```tsx
<Select value={selectedId} onValueChange={(value) => setSelectedId(value ?? undefined)} disabled={!operationsLoaded}>
  <SelectTrigger id="task-link-operation" className="w-56">
    <SelectValue placeholder={operationsLoaded ? "Select an operation" : "Loading..."} />
  </SelectTrigger>
  <SelectContent>
    {operations.map((operation) => (
      <SelectItem key={operation.id} value={operation.id}>
        {operation.title}
      </SelectItem>
    ))}
  </SelectContent>
</Select>
```

Passing the raw setter directly (`onValueChange={setSelectedId}`, without the wrapping arrow function) fails `tsc`: `Dispatch<SetStateAction<string | undefined>>` does not accept a `string | null` argument (`Type 'string | null' is not assignable to type 'SetStateAction<string | undefined>'`). The wrapping arrow function shown above coalesces `null` to `undefined` before it reaches the setter.
